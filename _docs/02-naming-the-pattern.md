## Learning objectives

By the end of this chapter you can:

- Explain what a pattern name actually compresses: a cluster of forces plus a chosen structure, not a block of code.
- Use a pattern name the way a team uses any shared vocabulary term, to let a reviewer reason at the level of the decision instead of the level of the syntax.
- Prompt an AI assistant with a pattern name precisely enough that the request constrains the forces, not just the keyword.
- Recognize a misapplied or needlessly heavy pattern an AI assistant emits, including the specific case of a virtual interface where a `std::function` or a concept would do.
- Explain why the skill of recognizing what to build, and why, matters more, not less, once a tool can generate fluent code for any pattern name instantly.

## Why this matters

A senior engineer says, in a code review comment, "this needs to be a Strategy, not a switch, because partner tiers are now owned by separate teams." The comment is one sentence. It lands because the author of the code under review, and everyone else reading the thread, already knows what forces that one word is standing in for: a requirement that varies, a requirement that is owned by more than one team, a cost that a switch statement cannot pay without becoming unreadable. Nobody has to re-derive the trade-off from first principles in the comment thread. The word does that work.

That compression is the entire value of a pattern name, and it is worth isolating from everything else the previous chapter covered, because the compression breaks in a specific, recoverable way once an AI assistant is part of the conversation. A model trained on a huge amount of code has also absorbed a huge amount of code that reaches for a pattern's name loosely, because the shape is familiar, not because the forces call for it. That means the same word that lets two engineers skip a paragraph of reasoning can also let an assistant skip the reasoning that was supposed to justify the word in the first place. This chapter is about keeping that compression accurate on both sides of that exchange, your side and the model's.

## A name is a compression, not a label

Chapter 1 built the vocabulary this chapter now puts to work: a force is a requirement that competes with another requirement in the same piece of code, and a pattern is the name a team gives to one recurring, specific way of resolving a particular cluster of those forces. The word "Strategy" is not a label stuck onto an abstract base class after the fact. It is shorthand for an entire paragraph: something in this code varies, it varies along a dimension the caller should not have to know about, and more than one way of varying it needs to coexist without forcing the caller to change when a new one is added. Say "Strategy" to someone who already shares that vocabulary and the paragraph arrives intact in their head. Say "abstract base class with virtual dispatch" instead and you have described a shape without saying why it exists.

This is why a pattern name survives being spoken out loud in a stand-up or typed into a one-line review comment, while a description of the code's structure does not. A shape is visible in the diff; the reviewer can see the base class and the overrides without being told. What is not visible in the diff is whether the forces that justify that shape are actually present in this code, today, for this team. The name is supposed to carry that judgment along with the shape. When it does, "this is a Strategy" is a defensible design claim. When it doesn't, the same sentence is decoration borrowed from a textbook, and the diff underneath it is paying for an abstraction that nothing in the actual requirements asked for.

The test for whether a name is still doing real work is simple to state and uncomfortable to apply consistently: can you unpack it back into the forces it is supposed to represent, right now, for this code, without reaching for the Gang of Four's definition from memory? If a teammate asks "why is this a Strategy and not just a function with a branch," and the answer is a paragraph about which requirements compete and which one wins, the name is still attached to the thing it is supposed to name. If the answer is "that's just what you do when a value needs to vary," the name has come loose from the forces that were supposed to justify it, and the question Chapter 1 trained, recognize the forces first, has not actually been asked.

## Reasoning at the right altitude

A team that shares pattern vocabulary gets something a team without it does not: the ability to have a design conversation at the altitude where the decision actually lives, instead of at the altitude of individual lines. Consider a pull request that introduces a connection pool for a billing service's database layer. A reviewer without shared vocabulary reads the diff line by line, checks that the mutex is acquired correctly, checks that the destructor releases the connection, checks that the tests pass, and approves. A reviewer who shares the vocabulary this book builds asks a different, prior question first: does this code actually need the correctness property a pool exists to provide, that no two callers ever receive the same live connection at the same time, or is a single shared connection with a mutex around it sufficient for the traffic this service actually sees? That question is only askable once "connection pool" is a name both people can hold in their heads as a claim about forces, not just a block of code to proofread.

This is also where the candidate non-pattern from Chapter 1 pays off in review, not just in design. A reviewer who has internalized the arc does not just ask "is this Strategy implemented correctly." They ask "was a switch statement considered and rejected for a stated reason, or did the pattern's name arrive first and the switch statement never get a hearing." A pull request description that says "implements Strategy for fee calculation" invites the first kind of review. One that says "fee calculation now varies per partner tier, owned by separate teams; Strategy over a switch because the switch would require every team to edit one shared function" invites the second, sharper kind, and it does so because the author did the forces-first reasoning before reaching for the name, which is exactly the habit Chapter 1 trained and this chapter is now applying to the review conversation itself.

The same altitude shift changes what a design document or an architecture discussion can accomplish in an hour. A meeting that spends its time re-deriving what a Factory is and is not, from first principles, every time the word comes up, has less time left for the actual decision in front of it: does this specific construction logic have the forces a Factory addresses, variation in which concrete type gets built, construction logic too involved to inline at every call site, or is `make_shared<ConcreteType>()` already the right answer and a Factory would be a Facade in front of nothing. Shared vocabulary does not make that decision for the team. It clears the table so the team can make it.

## The same word, read by a teammate and by an AI assistant

Every argument in the two sections above about a teammate reading a pattern name applies, almost unchanged, to an AI assistant reading one, and that is worth sitting with rather than rushing past. When you prompt an assistant with "add a Strategy for computing shipping cost, switchable at runtime between flat-rate and distance-based pricing," you are not just naming a code shape for it to produce. You are handing it the forces: something varies, the variation is selected at runtime, the caller should not change when a third pricing scheme arrives. An assistant that has the forces, not just the keyword, can make the same idiomatic choice a human engineer would, an abstract interface behind a `unique_ptr` here, a `std::function` holding a lambda there, because the forces, not the word alone, are what determine which idiomatic C++ expression actually fits.

The reverse prompt is where the compression starts to leak. "Make this flexible, use a design pattern" hands the assistant a word-shaped hole with no forces in it, and a model will reliably fill that hole with whatever pattern shape is most statistically familiar for code that looks like the surrounding context, whether or not the forces in your actual code call for it. This is not a flaw unique to AI tooling. It is the exact failure mode Chapter 1 opened with, the engineer who reaches for Strategy the moment an `if` statement crosses their field of view, run at a scale that can produce that outcome in seconds instead of after a weekend with the Gang of Four book. The fix is the same fix in both cases: supply the forces before the name enters the conversation, whether the name is about to come out of your own head or out of a model's.

This matters doubly for review, because an AI assistant's output is still code someone has to be accountable for, and the vocabulary this book builds is the fastest tool available for holding that code to the same standard a human co-author's code gets held to. A generated pull request that claims "implements the Observer pattern for cache invalidation" deserves exactly the same two questions a human-authored one does: what forces does this solve, and was a plainer alternative considered and rejected for a stated reason. The assistant will not ask those questions of itself unless the forces were in the prompt it received, which means the discipline Chapter 1 trained for a human engineer, naming a candidate pattern alongside a candidate non-pattern, is now also your primary review tool for a machine collaborator's output, not an optional afterthought layered on top of it.

## Recognizing an AI's misapplied or needlessly heavy pattern

The specific failure worth drilling on, because it shows up constantly in generated C++, is a virtual interface standing in for a choice that never needed runtime polymorphism at all. Ask an assistant for "a pluggable discount calculator" for a retail checkout flow and a common result looks like this: an abstract `DiscountCalculator` base class with a pure virtual `apply`, two or three concrete subclasses, a factory function that picks among them by an enum, and a `unique_ptr<DiscountCalculator>` threaded through the checkout path. Every piece of that is syntactically correct modern C++. None of it is wrong in isolation. And if the actual requirement is "pick one of three fixed discount rules known at compile time, with no plan to load a new one from configuration or a plugin," the entire inheritance hierarchy is solving a flexibility problem the code does not have, at the cost of a vtable indirection, three extra files, and a factory function nobody asked to maintain.

Recognizing this is the Chapter 1 arc applied to generated code instead of hand-written code, and it starts the same way: ask what varies, what is fixed, and whether the variation needs to happen after the program has already started running. If the three discount rules are fixed at compile time and selected by a configuration value read once at startup, a `std::function<Money(Money)>` assigned once during setup, or a template parameter if the choice is truly static, resolves the same requirement with no virtual call on the checkout hot path and no class hierarchy to navigate later. If a C++20 concept can constrain the shape a discount rule has to satisfy without naming a base class at all, that is worth putting on the table as the candidate non-pattern before the virtual interface is accepted as the answer. The question is never "is a virtual interface wrong." It is the same question Chapter 1 trained for a switch statement: does this code's actual forces call for runtime substitutability, or did the shape arrive because it is the shape a pluggable-anything request reliably produces.

The tell, once you are looking for it, is usually proportion rather than any one line of code. A hierarchy with one production implementation and a second that exists only to prove the interface is pluggable is the AI equivalent of the Strategy-for-an-if-statement from Chapter 1's opening scene, restated at the scale a model can produce it: fluent, syntactically clean, and paying rent for a future nobody has actually committed to building. Reviewing generated code for this pattern is not slower than reviewing hand-written code for it. It is the identical question, asked at the same altitude, regardless of who, or what, typed the diff.

## Why recognition matters more, not less, now

It is tempting to read the speed at which an assistant can produce a Factory, a Strategy, or an Observer and conclude that the vocabulary problem has gotten smaller, because the code itself is cheaper to produce than it used to be. The opposite is closer to true. When writing the code was the bottleneck, a certain amount of judgment was free: an engineer who had to type out an entire class hierarchy by hand had time, while typing, to notice that the hierarchy was solving a problem the code did not have. That friction is gone. A prompt that asks for "a flexible, extensible discount system" can produce the full virtual hierarchy, the factory, and a README describing its extensibility in the time it used to take to write one class, and the friction that used to catch an overbuilt abstraction partway through no longer exists to catch it.

That removes a safety net, it does not remove the need for one. The judgment that used to arrive as a side effect of the labor now has to be asked for explicitly, as a question posed before the prompt is sent and again before the diff is accepted: what are the forces here, and does this pattern, or the plainer alternative sitting next to it, actually answer them. That is not a new skill this chapter is inventing. It is the five-step arc from Chapter 1, recognize the forces, name a candidate pattern and a candidate non-pattern, choose the idiomatic expression, test the behavior, and know when not to use it, applied without exception to a collaborator that can produce any step of that arc on request except the first one. An assistant can generate a Strategy instantly. It cannot tell you, on its own authority, whether your checkout flow actually has a Strategy-shaped problem. That judgment call is still yours, and it is worth more now that the code around it is cheaper, not less.

Every pattern chapter from here forward hands you one more name to add to this shared vocabulary, always next to its own candidate non-pattern and its own "when not to use it" section, because the discipline this chapter just applied to review and to AI prompting is the same discipline those chapters apply to design. Part 2 takes the next step down into the SOLID principles that explain, in more formal terms, why some of these forces recur as often as they do. The catalogue grows from here. The habit of asking what a name is actually buying you, before you reach for it and before you accept it from a collaborator that reaches for it on your behalf, does not change.
